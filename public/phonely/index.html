Step 1 · Data analysis

Measuring the data's basic characteristics

3.28M vs 60,431context tokens vs reply tokens. The replies, the only tokens we train on, are 1.8% of the corpus, so training is inexpensive.
87%of context characters are system prompt (business configuration and rules).
664distinct turn instructions across the 2,000 records. They come from workflow templates, so the same instructions recur across many different calls.
  • How these were computed: a profiling script reads every record once, counting tokens with a tokenizer and reading the message structure from the role fields. No model calls, one linear pass, so the same profiling works unchanged on a corpus a thousand times larger.
  • Why these measurements: each feeds a setup decision. Token counts set the training configuration (loss is computed only on reply tokens, and 99% of records fit a 4,096-token window). Message structure determines what the prompt template must render correctly.
  • Caller text is speech-recognition output and it is rough: 31% of caller turns are one or two words, and transcription errors are common. Because many different replies can be valid at a given turn and the recorded reply is often imperfect, we score models by comparison (a judge picks the better of two candidate replies) rather than by similarity to the recorded reply.

Step 2 · Split design

Two leakage risks, and how the splits handle them

  • Risk one: 215 records are snapshots of the same 95 calls at different depths, so their contexts are near-identical. We found these by checking which records' contexts are string prefixes of one another, then assigned whole calls to a single split. Two snapshots of one call can never sit in train and test.
  • Risk two: more than a third of all records come from six businesses. Scores on those businesses would measure memorization as much as ability, so one test set contains five businesses whose records are excluded from training entirely.
  • Validation and test sets keep their defective records, labeled, because production input contains defects and the evaluation should measure behavior on them.

Step 3 · Rule-based checks

Rule-based quality checks over every record

  • A rule-based check is a small piece of code that tests one property of a record and answers yes or no. Code gives the same answer every time, runs over all 2,000 records in seconds, and scales to a corpus of any size. The same checks later run on every model's outputs, so the training data and the models are measured by one standard.
  • This is why these checks run before any model-based scoring: model calls cost money per record and can change their answer between runs. We save them for what code cannot judge, such as whether a reply sounds natural.
  • Every check comes from a rule the businesses wrote in their own configurations, or from a defect we saw while reading records. We did not invent style opinions.
  • Language: a language detector compares the reply's language to the caller's, because some businesses require English only and others require matching the caller.
  • One question per turn: count the question marks, because several businesses forbid asking multiple questions at once.
  • Spelled-out numbers: search for digit characters, because the voice system reads digits poorly and production replies write numbers as words.
  • Speech markup: some replies contain tags like <break time="300ms"/>, which tell the voice system to pause. We check that a model only produces tags from the small set that production actually uses.
  • Banned phrases: compare each reply against the exact phrases its own business forbids.
  • Duplicates and test traffic: compare normalized reply text across records, and search for the platform's own test phrases.
  • Where the checks came from, honestly: each pattern was discovered by reading records (human and LLM inspection of samples, the most frequent items, and the extremes), then turned into code that enforces it everywhere. Discovery cost is paid once on a sample; enforcement is free on the full corpus.
  • The banned-phrase lists are an example. Inspection showed that businesses write bans under a shared structural header in their configuration. A parser keyed on that structure then extracts the lists mechanically, and its cost scales with the 664 unique instruction templates, never with the number of records.
  • The same code measured what a normal reply looks like: 85% ask a question, digits appear in 0.2%, 13.2% contain speech markup, and replies average about 24 words. Tuned models are later checked against this profile.
  • The checks surfaced real problems: test calls placed by the platform's own engineers, one caller reading scripted gibberish, one business whose entire workflow is an advance-fee sweepstakes scam, one reply claiming to be a human agent, transcripts where the caller's television or hold-line audio was written down as if the caller had said it, and replies that break their own business's written rules.
  • They also prevented a filtering mistake: 128 replies are three-to-seven-word filler lines ("One moment, please.") because the turn's instruction asked for exactly that. A filter on reply length would delete correct behavior, so the judge rubric later states explicitly that an instructed filler is correct.
9 test-call records removed11 scam-script records removed2 gibberish records removed1 duplicate removed1 wrong-language reply removed1 human-impersonation reply removed128 filler replies weighted down in training16 TV/hold-audio transcripts weighted down
Removal is deliberately narrow: 25 records in total. Records with garbled speech, interruptions, and off-script callers stay in training, because handling them well is part of the job. At larger scale the same division of labor holds: an expensive judge labels a sample, a small cheap classifier trained on those labels sweeps the full corpus, and structured rules are enforced in code. In the product itself the extraction step disappears, because the platform owns the workflow format and rules arrive as structured fields at onboarding.

Step 4 · Privacy

A second pass to remove personal information

  • The vendor's scrub replaced phone numbers, emails, and card numbers. It largely missed people: real names survive throughout, about forty spoken dates of birth are age-consistent, and some full street addresses remain. We verified this by sampling records and checking each candidate span by hand.
  • This matters for training: fine-tuned models can memorize and reproduce rare strings. So we scrub before training and report the remaining gaps back to the data provider.
  • Our pass runs named-entity recognition (a standard tool that finds person names, dates, and addresses in text) over caller and agent turns, decodes spelled-out digits, and replaces each find with a substitute chosen deterministically per record. A caller keeps one consistent replacement name for the whole call, and reruns produce identical output.
  • Spans the pass could not classify confidently are logged with a reason instead of being silently skipped, so the gray areas are reviewable.

Step 5 · Model-based scoring

Scoring every training reply with an LLM judge

  • The rubric has five dimensions, each scored 1 to 5: follows this turn's instruction, grounded in the business configuration, sounds natural when spoken, handles the caller's actual words, and moves the call forward.
  • The dimensions come from the failure categories the rule-based checks surfaced, and the rubric encodes their exceptions: an instructed filler is correct, text-to-speech tags are legal, and length is not rewarded.
  • The judge scores each recorded reply next to Claude's rewrite of the same turn, in randomized order. One scoring run produced three outputs: the filter for the original-calls training set (score 18 of 25 or higher, instruction-following 3 or higher: 1,119 of 1,519 replies kept), 636 preference pairs for correction training, and a direct measurement of recorded-reply quality.

Step 6 · Rubric limitations

Where the rubric fell short, and what we changed

  • Score saturation. 78% of recorded replies score 4 or higher on naturalness (98% for Claude's rewrites), so absolute scores cannot separate two decent replies. All model evaluation therefore uses pairwise comparison instead of absolute scores.
  • Position bias. The judge reverses its verdict on 21% of pairs when the two replies swap display order. Every pair is judged in both orders, and only verdicts that agree across both count as wins or losses.
  • No global style rules exist. One business bans the phrase "are you calling about" while another business's script requires it word for word ("Are you calling about renting a home or buying a home?"). Phrase rules are therefore extracted per business and checked in code rather than left to the judge.
  • Blindness to illegitimate workflows. A scam script scores well on this rubric because the rubric measures faithfulness to instructions. The scam records are tagged and excluded from training. Catching this class of problem requires review when a business is onboarded; no per-turn evaluation can do it.

Step 7 · Generating targets

Generating better training targets with Claude

957 vs 307turns where the judge preferred Claude's rewrite vs the recorded reply (255 ties). Training on recorded replies inherits that quality gap.
1,980contexts rewritten by Claude Opus, cached to disk, generated at half price through the batch API
27%of rewrites contain "Got it". The teacher's habits transfer along with its quality, which matters in the failure analysis.
  • For this run, Claude Opus served as the reference and also produced the rewritten training targets.
  • Opus specifically for a structural reason: its API accepts a system message in the middle of a conversation, which is exactly where this dataset's per-turn instruction sits. The smaller Claude models do not accept that placement, so they would receive a distorted prompt.
  • Mechanics: one synthetic call-start turn satisfies the API rule that conversations begin with a user message (phone agents speak first). Every rewrite is cached with its request, so the training set can be rebuilt without regenerating anything.

Step 8 · Method constraints

Why true distillation was not possible

  • Distillation in the strict sense trains the student to match the teacher's token probabilities, and its on-policy variants score the student's own sampled tokens under the teacher. Both require the teacher's logits. The Anthropic API returns text only, and no open-weight model produces this product's behavior, so there is no teacher to distill from locally.
  • What the API does allow is imitation of the teacher's text. That transfers the teacher's choices without its uncertainty, which is one reason surface habits can transfer as unconditional reflexes.
  • The on-policy idea survives in a preference form: generate with our tuned model, keep the turns where it disagrees with and loses to the teacher, and train it to prefer the teacher's reply over its own. This targets the model's actual mistakes without needing logits.

Step 9 · Training setups

Three training setups, plus a capacity comparison

Tune on filtered original calls (baseline)Tune on Claude rewrites (main method)Correction pass on top (DPO)Same setup on a 30B model, 3.3B active
  • Base model: Qwen3-4B-Instruct. The requirements that drove the choice: the chat template must render a system message mid-conversation (verified with unit tests, since some templates drop or relocate it silently), about 2% of traffic is non-English, and the license must permit commercial use. Llama 3.2 requires an access application and Gemma's template has no system role.
  • Training uses LoRA adapters: a small trained add-on over a frozen base model, which keeps runs cheap and repeatable. The loss mask was verified token by token on decoded samples before any GPU spending.
  • The correction pass exists in two versions. The first built 636 preference pairs from judge verdicts over the recorded replies. The second generator constructed 1,125 candidate pairs from materially different student replies, treating the teacher reply as preferred by construction; the length filter dropped 10, so training consumed 1,115. The negative-results section shows why this difference decided the outcome.
  • The 30B model is a mixture-of-experts design: it stores 30 billion parameters but activates only 3.3 billion per token, which is what the task's size limit counts. It runs the identical recipe, so any difference in results is attributable to model size and nothing else.

Step 10 · Evaluation

How models are compared

  • Two models' replies to the same turn go to a judge model that sees the call, the business configuration, and this turn's instruction. The judge is a different Claude model from the teacher, so it is not grading its own writing.
  • Each pair is judged twice, once in each display order. Win rates average the two orders with ties counted half, and confidence intervals come from resampling records.
  • A second judge (Claude Fable, a different Claude model from both the main judge and the teacher) re-scored 50 comparisons. It agreed with the main judge on 78% of them and ranked the models in the same order.
  • The rule-based checks from step 3 run on every model output. A blind human comparison over the closest pairs has been prepared and remains pending.

Step 13 · Regressions

Failures introduced by fine-tuning

  • Our model violates the ban on 13 of 29 covered replies, and every violation is the identical sentence. The habit traces to the teacher: 27% of Claude's rewrites contain "Got it". Claude itself complies when the ban is in its prompt; the student learned the phrase without the per-business condition.
  • 36 of the 148 clear losses to Claude Opus are also turns where the judge rates our model below its own untuned starting point. Fine-tuning introduced those failures.
  • The other linked cases: a condolence for a death that never happened, and a reply that speaks as a real named person.

Step 14 · Negative results

Negative results and what each one changed

  • The first correction pass produced no change: 49.8% and 50.3% against our model, statistically a coin flip. The cause: its training pairs came from the recorded replies, so it practiced against mistakes our tuned model no longer makes. A preference pass can only fix mistakes the current model actually produces.
  • The second correction pass built 1,125 candidate pairs from materially different model replies, treating the teacher reply as preferred by construction; the length guard dropped 10, so 1,115 reached training. Its success criterion was fixed in advance: the 13 banned-phrase violations should drop. They did not (11 remain). Head to head with its starting model it is a tie (49.7% and 52.2%). Against Claude Opus it scores 33.8% and 33.7%, nominally above 31.2% and 29.7%, in the same direction on both test sets but within overlapping confidence intervals.
  • The banned-phrase miss has a structural cause we can now state with evidence. The ban exists only at a held-out business. The training pairs come from businesses where the phrase is legal and the teacher uses it freely, so not one pair penalizes the phrase. Weight training cannot learn a rule that never appears in its training signal; this failure class needs the rule checked in code when the reply is generated.
  • We also tested whether the improvement really lives in the trained weights: give the untuned model the same style guidance in its prompt instead. Win rate stayed flat (13.3% without the guide, 14% with it), so prompting does not substitute for the tuning here.

Failures that require workflow changes

2/4 vs 0/4danger probes passed with the priority rule in the prompt: untuned model vs our tuned model
4/4 → 1/4unsupported-claim probes passed, before vs after tuning: tuning traded caution for confident assertion
18 × 6frozen probe scenarios, run on three models with and without the rule
  • The probe results settle the prompt question. On the four acute-danger scenarios no model pauses the script by default. Adding a priority rule to the prompt lifts the untuned model to 2 of 4 and moves neither tuned model off zero. Fine-tuning entrenched the workflow so deeply that a prompt-level rule cannot override it, so the distress behavior needs training examples or an enforcement layer outside the model. A prompt rule alone is not enough.
  • The probes also caught a second cost of tuning: the untuned model passes the unsupported-claim scenarios because it hedges, while the tuned models confidently assert account facts they cannot know. The checker is lexical and conservative, so individual verdicts deserve human review, but the direction is consistent with the condolence and impersonation cases.
  • The scam case needs vetting when a business is onboarded. Training the model to refuse mid-call would teach it that ignoring a business's instructions is sometimes correct, and that behavior is more dangerous than the problem it would fix.

Step 16 · Limitations

Limitations of this evaluation

  • The teacher and both judges are Claude models. We used three different ones and added rule-based checks, but the planned blind human comparison is still pending, so a shared-family bias may remain.
  • 2,000 records is a small dataset. The confidence intervals in the charts carry that uncertainty.
  • Training and judging happen one turn at a time. Behavior drift across a long conversation is untested.
  • A rented GPU instance failed mid-run. We retrained with the identical recipe and seed, then regenerated and re-judged the test outputs from the retrained model as a check: 32.7% and 35.9% against the reference, consistent with the originals (31.2%, 29.7%) at these sample sizes.
  • All main comparisons use greedy decoding on both sides. A control with sampled decoding scores 33.5% on validation against the reference, next to 33.2% for greedy, so the results are not an artifact of the decoding choice.

Step 17 · Next steps

What we would do next

  • Build the rule-check layer the correction-pass result showed is necessary: extract each business's bans and constraints at onboarding, verify every candidate reply in code, regenerate on violation.
  • Give the distress behavior training examples and an enforcement layer outside the model; the probes showed a prompt rule alone does not move a tuned model.
  • Run a recurring correction loop on data that includes rule-carrying businesses: collect the live model's worst turns, obtain Claude rewrites of them, train against them.
  • Serving: the 4B model with the adapter merged runs on one small GPU and fits phone-call latency.
